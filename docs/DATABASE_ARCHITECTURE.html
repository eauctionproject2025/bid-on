1. Purpose

This document describes the logical and physical database design for Bid On: entities, relationships, money and escrow rules, indexes, and hosting notes. It is suitable for management review, audit, and engineering handoff.

3. Design principles

  1. Single source of truth — auction, bid, escrow, and KYC state live in PostgreSQL.
  2. Role-based access — buyer, seller, admin on User.role.
  3. Listing moderation — lots start pending until admin approval.
  4. Escrow before settlement — winner payment recorded as held before release.
  5. Money as Decimal — Decimal(12,2) for prices and bids.

4. Entity catalogue

4.1 User

Identity, roles, email verification, password reset OTPs, KYC and bank verification, rating aggregates.

GroupFields (summary)
Identityid, name, email (unique), passwordHash
Accessrole, verified, suspended
KYC / Bankstatus enums + document / account fields + review timestamps
ReputationratingAvg, ratingCount

4.2 Category

Hierarchical catalogue (parentId self-relation). Unique slug for filters.

4.3 Auction

Listing content, pricing (startPrice, optional reserve / max cap), currentBid, minBidIncrement, clock (endsAt), status, winner.

pending → (approve) live → (end) ended pending → (reject) cancelled ended + paid escrow → sold path

4.4 Bid

Immutable history rows. Opening bid may equal start price; later bids add increment. Auction row is locked during place-bid to prevent race conditions.

4.5 Watchlist

Unique pair (userId, auctionId).

4.6 Notification

Typed alerts with optional JSON meta. Indexed by (userId, read).

4.7 Transaction (escrow)

Links auction, buyer, seller, amount, Stripe ids, hold/ship/dispute timestamps.

pending → held → completed ↘ disputed → completed | refunded ↘ failed | refunded Unique: stripeSessionId Index: (auctionId, status)

Note for management: Release marks funds completed in the ledger. Automated Stripe Connect payout to seller bank accounts is recommended as Phase 2.

4.8 Review

Unique (auctionId, fromUserId). Feeds user rating aggregates.

8. Security summary

  • Passwords stored as bcrypt hashes.
  • JWT_SECRET required in production (min 16 characters).
  • CORS locked to configured frontend origins in production.
  • Socket notification rooms require authenticated user.
  • KYC file privacy: recommend private object storage (Phase 2).
